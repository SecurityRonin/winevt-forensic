# 6. MSRV floor of 1.75 under a pinned 1.96.0 dev toolchain

Date: 2026-07-24
Status: Accepted

## Context

The suite is developed on the current fleet-pinned stable toolchain but its
library crates are meant to be *linked* by third parties and other fleet repos
(`winevt-integrity`, `winevt-carver`, `winevt-core`, … are published for reuse).
The constitution separates two concerns that are easy to conflate:

- The **dev toolchain** — what contributors build/fmt/clippy with — is pinned to
  one current stable across the fleet to end version drift.
- The **declared MSRV** (`rust-version`) is a downstream-facing promise. For
  published libraries it is kept low and CI-verified, because raising it narrows
  the crates.io audience and is a near-breaking change.

Raising a library's MSRV just to match the dev toolchain throws away a real
compatibility guarantee for no feature gain.

Evidence: `rust-toolchain.toml` (`channel = "1.96.0"`, plus clippy/rustfmt
components); workspace `Cargo.toml` `[workspace.package] rust-version = "1.75"`
inherited by every member (`rust-version.workspace = true`); commit `0d3f41a`
(`pin toolchain to 1.96.0 (fleet toolchain policy)`) landing *without* changing
the declared 1.75. Constitution: "Rust MSRV & Toolchain Policy" and the fleet
"Published libraries keep a low CI-verified MSRV".

## Decision

1. Pin the dev toolchain to the fleet stable (`1.96.0`) in `rust-toolchain.toml`,
   the single source of truth for the build version.

2. Declare `rust-version = "1.75"` at the workspace level so all published
   library crates promise a low, stable MSRV floor independent of the drifting
   dev pin.

3. Raise the declared MSRV only if a crate genuinely needs a newer-Rust feature —
   never merely to track the toolchain.

## Consequences

- The published `winevt-*` libraries remain installable on Rust as old as 1.75,
  a deliberate reuse feature and README trust signal (`Rust 1.75+` badge).
- Contributors and CI build on one modern toolchain, so fmt/clippy stay
  consistent while the compatibility promise is unaffected.
- The CLI (`winevt-cli`) also inherits 1.75; nothing pins a library dependency
  against it, so this is conservative rather than harmful. If a future capability
  dep forces a floor bump, that is a deliberate, documented change, not a drift.
